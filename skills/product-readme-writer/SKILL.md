# 产品 README 写作

把 README 写成产品入口页。读者应在几分钟内知道产品是什么、为什么值得用、能解决什么问题、如何获得帮助。

## 先判断任务范围

先区分根目录 README 和技术文档：

- 根目录 README 面向普通用户、下载者和潜在使用者。
- `docs/`、开发说明和 API 文档面向开发者。
- 根目录 README 不放构建命令、测试日志、Git 提交、目录结构、ABI、内部 crate 名、CI 说明或仓库治理信息。
- 用户没有要求时，不把 README 写成开发者手册、验收报告或项目交接文档。

## 先查证产品，再写文案

按以下顺序调查：

1. 阅读现有 README、产品界面文案、用户指南和限制说明。
2. 阅读实际入口、设置结构和主要调用路径，确认功能确实存在。
3. 区分三个状态：已实现、用户可以操作、已在真实环境验证。
4. 只把已实现且用户可理解的能力写成产品卖点。
5. 对不确定的功能保留谨慎措辞，或不写入产品 README。

不要根据目录名、规划文档、上游功能或测试名称推断产品已支持某项功能。不要把上游 Linux/macOS 功能写成当前 Windows 产品能力。

## 先找第一卖点

先用一句话回答：用户为什么要选择这个产品？

第一卖点应出现在：

- 标题副标题。
- “是什么”首段。
- “为什么使用”第一条。

如果产品的核心优势是本地运行和隐私，直接写清楚：

- 输入引擎和必要数据在哪里运行。
- 普通输入是否需要网络。
- 正在输入的内容是否发送到服务器。

不要把第一卖点埋在“数据和隐私”章节，也不要用一长串次要功能稀释它。

## 组织用户内容

推荐使用以下结构。按产品复杂度删减章节，不要为了完整而全部保留：

1. 产品标题和一句定位。
2. 产品是什么。
3. 软件预览或关键界面。
4. 为什么使用：3 到 8 条核心卖点。
5. 数据和隐私。
6. 系统要求。
7. 常见问题。
8. 相关文档。

如果产品有大量能力，把它们归并成少数主题。输入法可以归并为：

- 本地输入和隐私。
- 拼音与候选学习。
- 中文英文混排。
- 词库迁移。
- 常用工具。
- 候选窗和个性化设置。

每个主题用一句结果导向的说明。只有在用户需要完成任务时，才列出具体格式、按键或示例。

## 避免流水账

不要把每个开关、每个快捷键、每个文件格式都列在“主要功能”里。下面这些内容通常应进入详细文档：

- 完整按键表。
- 所有配置项。
- 每个导入格式的逐行语法。
- 内部数据目录和日志细节。
- 组件、进程、管道和模块名称。

根 README 只保留能帮助用户选择和开始使用的内容。详细说明通过链接提供。

## 写作规则

使用短句和具体动词：

- “输入引擎在本机运行。”
- “导入词库后，词条参与候选排序。”
- “候选窗支持横排和竖排。”

避免：

- “旨在”“致力于”“全面赋能”等空话。
- “轻量”“极速”“安全可靠”等未经数据支持的宣传词。
- “当前阶段”“测试版”“尚未验收”“不可用”“暂不支持”等项目状态描述，除非用户明确要求披露产品状态或这些信息直接影响使用。
- 对用户没有帮助的否定式功能清单。
- 把实现过程写成用户步骤。

如果产品确实有一项重要限制，应使用简短、可行动的说明，并放在常见问题或系统要求中。不要用限制章节压过产品价值。

## 中英文 README

中英文内容要一一对应：

- 产品定位一致。
- 第一卖点一致。
- 功能分组一致。
- 图片顺序一致。
- 链接目标一致。
- 语气自然，不逐字翻译中文长句。

修改中文结构后，立即同步英文结构。不要让英文 README 保留已经从中文删除的“快速开始”、测试状态或开发者内容。

## 图片预览

图片是产品 README 的内容，不是装饰。

先确定图片来源：

- 优先使用真实安装版界面或生产组件渲染。
- 如果用本地渲染生成，确认渲染路径使用真实生产组件和真实配置。
- 不要把设置页中的候选窗预览误当作实际候选窗截图。
- 候选窗预览只放候选窗本身，不带设置页和无关窗口。

统一图片规则：

- 设置页图片使用同一尺寸。
- 页面内容完整显示，不截断主要内容，不保留滚动条作为主要画面。
- 多张设置页中把“常规”或总览页放第一张。
- 同一组图片使用稳定的文件名和目录。
- 公开图片不得包含邮箱、文件路径、账号、私人词库、个人日志或其他本机数据。
- 每张图片都应有准确的 alt 文本。
- 图片尺寸、来源和二进制登记按仓库规则处理。

推荐使用 HTML 表格并排展示同类图片。图片数量要服务于理解，不要为了“随机多张”堆图。

## 用户可见的隐私说明

隐私文案必须与实际数据流一致。分别确认：

- 普通输入是否联网。
- 哪些数据写入本机。
- 剪贴板历史是否默认关闭。
- 哪些可选功能会访问网络或外部服务。
- 备份是否包含个人输入习惯。

如果存在用户主动配置的外部服务，准确说明发送的内容和发送对象。不要把“普通输入本地运行”扩大成“所有功能永远不联网”。

## 最终审核

写完后逐项检查：

- 标题是否直接表达第一卖点。
- 首段是否说明产品是什么和核心价值。
- “为什么使用”是否只有少数重点。
- 是否还残留测试版、开发状态、构建命令或仓库术语。
- 是否存在功能流水账。
- 中英文结构和卖点是否一致。
- 图片是否完整、同组同尺寸、无私人信息。
- 图片链接和文档链接是否存在。
- 文案是否把未核实能力写成已支持能力。
- 读者只看前两屏时，是否已经理解产品价值。

验证 README 修改时，运行项目定义的文档、链接、仓库卫生和相关测试检查。检查通过只能证明文档和仓库规则通过；不要把它写成产品功能验收结论。
