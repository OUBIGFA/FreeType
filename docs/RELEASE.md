# FreeType 打 tag 与发布流程

本流程于 2026-11-13 确认。只在用户要求发布、打 tag，或任务将操作发布标签、Release、公开安装器时读取。普通开发任务不预读。

## 固定约定

- 发布目标为 `OUBIGFA/FreeType`，源码来自 `main`，只向 `origin` 推送。不向 WowType 上游推送，不迁移其分支、标签或 Release。
- 产品版本为 `X.Y.Z`。默认发布标签为 `freetype-X.Y.Z`，使用带说明的 annotated tag，不包含额外的 `v`。本次用户指定首发版本及裸标签 `0.1.0`；草稿须明确这个标签，确认后才创建。更新检查兼容两种格式，并要求安装器文件名的版本与标签一致。
- Release 标题为 `FreeType X.Y.Z`。公开附件只提供对应版本的安装器 `FreeType-X.Y.Z-Setup.exe`，不附带便携包、SHA-256 文件、构建记录或临时产物。
- 安装器对应的 `.sha256` 和 `build-info.json` 保留在本地及 CI 构建记录中，不入库、不作为 Release 附件。构建记录包含标签、实际源码提交及源码树、内部构建号、依赖与工具链版本、安装器 SHA-256。
- 支持范围为 Windows 10/11 x64。安装器包含 x64 应用及 x64/x86 输入法 DLL；包含 x86 DLL 不表示支持纯 32 位 Windows。
- 安装标识保持为 `io.github.oubigfa.freetype`，用户数据目录保持为 `%APPDATA%\FreeType`。不通过改变名称、版本规则或数据目录回避覆盖安装兼容。
- 日常代码任务仍按固定测试安装器约定交付：版本 `0.0.1`，路径 `output/release/FreeType-0.0.1-Setup.exe`，同时更新校验文件与构建记录，再提交并普通推送 `origin/main`。这不自动授权公开发布。
- 正式版本与固定测试版本使用同一构建入口的不同参数及输出位置。正式版本通过临时构建配置注入，应用显示版本、安装器版本和 Release 版本一致；不修改已经打 tag 的源码，不把旧固定测试包改名上传。
- 已实现入口：`windows/build.ps1 -Version X.Y.Z` 构建本地候选；`-Version X.Y.Z -ReleaseTag <已批准标签>` 仅接受该标签的干净检出且强制运行测试。输出分别为 `output/candidates/X.Y.Z/` 和 `output/releases/X.Y.Z/`。脚本不会创建标签、Release 或上传安装器。
- 线上入口为 `.github/workflows/windows-build.yml`（FreeType Windows installer）。手动运行指定版本时只构建候选；推送 `0.1.0` 或 `freetype-X.Y.Z` 标签时调用同一脚本的精确标签模式。工作流在 Windows Server 2022 上准备项目内固定工具链、重建公开词库并运行全部测试。
- 线上任务只读仓库，不创建 Release。其 CI Artifact 仅保存对应安装器、SHA-256 文件和 `build-info.json`，用于下载后核对；GitHub Release 的公开附件仍只有安装器。构建成功不表示 Windows 10/11 的真实安装、升级或 UAC 验收通过。

## 1. 先提供对话中的 Release 草稿

收到“打 tag 发布”“发布”或“打 tag”等请求后，先进行与草稿有关的只读调查。核对当前源码、用户指定的版本、上一份 FreeType Release 和本次变化，再在对话中展示草稿。不要按上游 WowType 的版本说明比较。

草稿必须包含以下确认项：

- 产品版本、标签、Release 标题。未指定版本时提出建议并标为待确认，不自行决定首个发布版本。
- 发布类型：正式版或预发布。预发布必须正确设置 GitHub 的 Pre-release 标记，不能因构建通过就标为稳定版。
- 目标源码提交；若还有待处理改动，说明它们及提交尚未固定的事实，不把当前 HEAD 当成最终源码。
- 公开附件名 `FreeType-X.Y.Z-Setup.exe`。安装器还未构建时，SHA-256 和产物验收结果明确标为待生成、待验证。
- Release 正文、已完成的验证和仍未满足的发布条件。验证状态放在确认项中，不把构建日志塞进面向用户的正文。

Release 正文使用简体中文，按当前版本相对上一份 FreeType Release 的变化编写。首次发布只说明实际已有且已验证的功能。按需要保留以下章节，不机械保留空章节：

```markdown
FreeType X.Y.Z：<一句话说明本版主要变化>。

## 主要更新
- <用户能看到或使用的变化，以及必要的默认值和适用条件>

## 稳定性改进
- <修复的实际问题，以及生效范围>

## 配置兼容性
- <旧配置和用户数据是否继续可用，是否需要操作>

## 已知影响
- <影响安装、升级或使用的限制，以及用户需要采取的动作>
```

草稿是对话中的待确认文案，不是 GitHub 的 Draft Release。提供草稿后等待用户回复；确认前不创建或推送标签、不创建远端 Release、不上传安装器。此前同意流程、完成代码任务或确认其他版本，不代替本次草稿确认。

用户确认当前草稿后，授权只覆盖本次确认的版本、正文、发布类型、目标源码范围、标签和安装器附件。后续核对无需对同一范围重复索取确认；版本、正文、源码范围、发布类型或附件有实质变化时，重新提供草稿并等待确认。

## 2. 发布前检查

用户确认草稿后，按以下顺序检查。与草稿有关的安全只读检查可提前进行：

1. 阅读 [仓库边界](../references/repository-boundaries.md)、[第三方来源与许可](../third_party/README.md) 和 [Windows 安装与验证范围](WINDOWS.md)，按实际状态处理未满足条件。
2. 区分并保留其他任务的改动。目标提交包含本版全部实现、必要文档、锁文件和测试；不把未经确认的改动一起暂存或提交。
3. 核对工作区、暂存差异、跟踪清单及全部远端 heads/tags。确认目标提交已在 `origin/main`，新标签在本地和远端都未占用，没有凭据、机器路径、私人词库、学习记录或发布产物混入 Git。
4. 核清引擎、依赖、词库及模型的许可依据。按 [随包总声明](../third_party/NOTICE.md) 检查 `THIRD-PARTY-NOTICES.txt`、`third-party/manifest.json`、许可原文及对应源码；复核 GPL 数据原始声明和转换输入的提供方式。只有 manifest 中的许可名称不代替缺失的许可证文本或授权依据；预发布也不能绕过许可检查。
5. 固定本次 Rust、Go、mygo、NSIS 版本及公开数据输入的修订和摘要。按固定修订重建或下载，不使用浮动 `latest`，不依赖本机未登记的 `.local/` 内容。
6. 确认正式版本构建参数和发布工作流已经实现且验证可用。先用不发布模式试跑；缺少这些能力时停在打 tag 之前，不用文档中的目标流程冒充已有能力。
7. 运行 `python -X utf8 tools/check_repo.py`、`python -X utf8 -m unittest discover -s tests/repository -v`，并按统一构建入口完成受影响测试及必要构建。正式发布不得使用 `-SkipTests`。
8. 确认可用的隔离测试环境和安装验收授权，执行 [Windows 隔离验收清单](WINDOWS-ACCEPTANCE.md) 并保存本次包的证据。不自动安装、升级或卸载用户现有的 FreeType，也不操作用户正在使用的应用实例。清单中的“未执行”项不等于通过。

## 3. 打 tag、构建并生成 GitHub 草稿

1. 对已确认且已检查的提交创建草稿中指定的 annotated tag，本次为 `0.1.0`。标签说明使用简短中文摘要，详细变化放在 Release 正文。
2. 只向 `origin` 推送本次指定标签。不得使用 `git push --tags`，不得覆盖标签、强制推送或顺带创建分支。
3. 发布工作流只匹配 FreeType 发布标签。从该标签指向的提交开始，在干净 Windows 环境中检查仓库、运行 Rust/Go 测试，再构建应用、x64/x86 DLL 和安装器。不能用另一次分支构建结果代替。
4. 运行 `powershell -File windows/build.ps1 -Version X.Y.Z -ReleaseTag <已批准标签>`，通过临时构建配置生成 `FreeType-X.Y.Z-Setup.exe`、SHA-256 和构建记录。核对实际源码提交、源码树、版本与数据摘要，不把提交前的包标成另一个提交的产物。
5. 只有构建和产物检查通过，才创建 GitHub Draft Release。使用已确认的标题与正文，附件采用精确白名单且只包含本次安装器；缺失文件或名称不匹配时失败，不使用通配符上传整个输出目录。

## 4. 验收后发布并复核

1. 核对远端标签实际指向的提交、CI 运行的源码提交、构建记录及安装器版本。应用显示版本、安装器版本、标签中的版本和 Release 版本必须相同。
2. 获取这一次 CI 安装器，先核对 SHA-256，再在已授权的隔离测试环境中验收。旧固定测试包、只有构建成功或只有工作流返回成功，都不能代替这一次产物的验收。
3. 按隔离验收清单检查首次安装、管理员授权与取消、TSF 注册、输入法启用、实际 x64/x86 应用输入、同版本不同构建覆盖、卸载及配置和用户数据保留。正式版还需验证从最后测试版到正式版的升级；失败时保留证据并停止发布，不用旧包的结果代替本次产物。
4. 核对 GitHub 草稿正文、发布类型和附件，确认与用户批准内容一致。有实质变化时回到对话草稿确认步骤；没有变化时不重复询问。
5. 在本次确认范围内发布 Release。复核其不是 Draft、Pre-release 状态符合确认结果、标题和正文正确、附件只有 `FreeType-X.Y.Z-Setup.exe`，附件摘要与已验收安装器一致。
6. 向用户交付 Release 链接、版本、标签、源码提交、安装器 SHA-256 和实际验证结果。不为修改 Release 正文额外提交源码，不把计划或工具返回成功当成发布完成。

## 失败处理与能力边界

- 任何必要检查失败时，停止依赖它的后续步骤，说明具体问题、已完成内容和下一步。继续完成不依赖阻碍的部分，不吞错、不交付旧包。
- 纯构建环境故障可以对同一标签重跑；需要修改源码时使用新版本，并重新提供 Release 草稿。默认不移动、删除或复用已有标签，不替换已公开安装器。
- 本流程的确认不授权新分支、强制推送、改写历史、修改其他仓库或操作用户已安装的应用。

## 首次发布尚未满足的条件

2026-11-14 复核后的剩余条件：

- 本地测试包已接入许可原文、对应源码、声明清单和五个文件的版本资源检查，但这不表示下面的发布条件已满足。
- WowType 固定修订的 README 明确提供双许可，已选择 Apache-2.0 并保留标准全文与授权证据。默认数据对应源码、模型署名、Unicode CLDR 声明和其他随包义务已纳入收集与校验。该结论限于本次 Windows 包，不扩张到未打包的上游资源；仍须核对最终包的清单与摘要。
- `windows/build.ps1` 和线上 Windows 安装器工作流已有独立版本与精确标签构建入口。线上入口仍须先运行不发布预演，并核对本次标签实际运行的产物；不得把本地候选、手动分支构建或仓库检查 CI 冒充标签构建产物。不能用固定测试包改名代替正式版本。
- [隔离验收清单](WINDOWS-ACCEPTANCE.md) 尚未在隔离测试机执行。卸载取消授权的静态风险已修复并覆盖失败回归，但自动测试、版本资源检查和一次性夹具不代替真实安装、升级、UAC 与应用内输入验收。

可以先提供标注上述待办的 Release 草稿供审阅，但条件解除且当前草稿获确认前，不创建发布标签或远端 Release。
